# Current findings

- The shipped model still owns a seven-state goal lifecycle; required checks and completion evidence live in goal contracts, not a standalone `.ai/verification.toml`. [Architecture direction](../../docs/architecture-direction.md) selects native harness tasks and project-owned verification for a future model; it does not supersede accepted ADRs or implement that transition.
- Historical DONE evidence also drives `doctor`: product changes require reopening and reverifying accepted goals. Git ancestry is required as well; squash/rebase can invalidate identical verified content. Harness-setup, terminal-menu, and post-mvp-hardening have passing evidence at 6f45f36.
- The supplied architecture context ends mid-sentence in its capability-layering section. Decisions use the complete sections; no requirements were inferred from the missing ending.
- Profile selection edits only the modules array and refuses unfamiliar formatting (including comments inside that array) with manual-edit guidance. Sync is nontransactional: if a generated-file write fails, the saved profile stays visible so doctor/sync --check cannot conceal partial updates behind a profile-only rollback.
- Setup uses schema-2 managed instruction blocks and a pending operation; legacy init/adopt use schema 1 until explicit setup. Baseline discovery runs against the private original snapshot and cannot replace a known failing command. Setup evidence is local validation, not a tamper-proof attestation; ADR 0005 extends the shipped model without implementing the future lifecycle migration.
- Run goal verification sequentially: temporary files from concurrent goal writes can trip the clean-product guard. Managed block ownership is restricted to AGENTS.md, AGENTS.override.md, and CLAUDE.md; application source cannot be promoted into that scope through the lock.
